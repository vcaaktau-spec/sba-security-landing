# PLAN — Интерактивный подбор оборудования (SBA Security, toosba.kz)

> Синтез цепочки greenfield-планирования: `BRIEF.md` + `research.md` + `architect.md` + `pm.md` + `security.md`. Это не greenfield-проект, а большая фича поверх существующей кодовой базы (`Calculator.tsx` не трогаем по содержанию). GSD-формат: практично, конкретно, без воды.

## 1. Overview

Сейчас на `toosba.kz` есть один путь расчёта — пошаговый квиз-калькулятор по абстрактным тирам оборудования (камеры/разрешение/монтаж), без привязки к реальным товарам. Задача — добавить второй, главный путь: пользователь либо отвечает на несколько наводящих вопросов и получает 2-3 готовых набора оборудования от Gemini, либо сам собирает комплект из каталога товаров. Оба варианта ведут в общую корзину, из которой считается смета (оборудование + монтаж, с переиспользованием существующей ценовой логики) и генерируется скачиваемый PDF/КП. Старый калькулятор остаётся как второстепенная опция "быстро посчитать монтаж".

Продукт нужен для двух разных аудиторий сразу: частник/малый бизнес, которому важна наглядность и скорость, и снабженец крупной компании, которому нужен официальный, тендер-совместимый документ. Ключевой вывод исследования рынка — эта связка ("AI/ручной подбор → каталог → корзина без чекаута → смета с монтажом") не имеет прямого готового референса в CCTV-нише: у дистрибьюторов нет монтажной сметы, у локальных монтажников нет каталога и подбора. Это реальная точка дифференциации, но и зона, где придётся проверять решения на реальных данных, а не копировать чужой паттерн.

Три вещи определяют всё фазирование ниже: (1) наполнение и поддержание каталога данными без машиночитаемого фида от поставщика — самая недооценённая по срокам часть; (2) точность AI-рекомендаций требует нескольких раундов реального тестирования на живом каталоге, а не на тестовых 10-15 позициях; (3) юридическая формулировка "цены ориентировочные" должна быть согласована на всех поверхностях — Hero, корзина, PDF — иначе это репутационный и потребительский риск. План разносит AI и полный редизайн на более поздние фазы именно поэтому — не потому что они не важны, а потому что запускать их раньше готового каталога бессмысленно.

| AI-рекомендации | Google Gemini API, `responseSchema`/structured output, не function calling | Structured output даёт валидный JSON без хрупкого парсинга текста, дешевле и предсказуемее по латентности, чем оркестрация function-calling — для домена (передать отфильтрованный каталог + вопросы, получить фиксированную схему `bundles[]`) это прямое попадание. Вызов только из serverless (`api/`), ключ не в браузере. |
| PDF/КП | jsPDF + html2canvas (переиспользование существующего паттерна как отдельный модуль `renderSmetaPdf()`) | Уже работает для старого калькулятора, не требует новой зависимости. Известное ограничение — плохо масштабируется на многостраничные таблицы с разрывами страниц; для MVP-объёма позиций (5-15 строк) это не проблема, откладываем миграцию на серверный рендеринг (Puppeteer/React-PDF) до реальной необходимости. |
| Хостинг/инфраструктура | Vercel (serverless `api/`), Neon Postgres, Vercel Blob (фото/PDF) | Без изменений — весь новый функционал укладывается в уже работающий контур, без новых сервисов. |

## 4. Architecture (сжато)

**Где живёт фича.** Новый флоу встраивается в `Home.tsx` как второе независимое модальное состояние (`isPickerOpen`), по образцу уже работающего `isCalcOpen` → `<Calculator>`. Новый компонент — `src/components/EquipmentPicker/` с внутренними шагами `mode-select → (ai-quiz | catalog) → cart → estimate/pdf`. `Calculator.tsx` не меняется, ничего из него не импортируется — только `src/lib/pricing.ts` (уже общий, безопасный модуль). Опциональный отдельный роут `/katalog` — единственное место, где потребуется аддитивная правка `App.tsx` (danger zone); решение отложено (см. Clarifications #5).

**Модель данных.** Две новые таблицы, `equipment_prices` (ценовой кэш тиров для старого калькулятора) не трогается и не путается с новым каталогом:
- `products` — конкретные SKU: категория (enum, без отдельной таблицы `categories` на MVP), фото (Vercel Blob URL), jsonb `specs`, денормализованный `environment` (indoor/outdoor) для быстрой фильтрации, `basePrice`, опциональная ссылка `priceTierKey` на `equipment_prices.key`, `active`/`sortOrder`.
- `quotes` — след пользовательского расчёта: `mode` ('ai'|'manual'), `items` (productId+qty+unitPrice), `installParams`, `estimateTotal`, контакты (только на этапе явной отправки заявки), `aiTranscript` (если mode='ai'). Создаётся только по явному действию пользователя ("получить КП"), не на каждое изменение корзины — так же, как `Calculator.tsx` шлёт в Telegram только по сабмиту.

**Границы модулей.** Каталог (`src/lib/catalog.ts` + `api/products.ts`) → Корзина (`useCart` hook, Context+localStorage) → Смета (`src/lib/estimate.ts` + `pricing.ts`) → PDF (`src/lib/pdf/`). Модули друг про друга напрямую не знают (каталог не импортирует корзину и т.д.) — тестируются независимо. Единственная точка, знающая про все четыре — `EquipmentPicker.tsx`.

**Как работает AI-эндпоинт (`api/ai-recommend.ts`).** Ключевое решение: **AI — надстройка над rule-based фильтром, не замена**. Поток: (1) клиент шлёт ответы квиза (без ПДн — только параметры объекта); (2) сервер делает rule-based префильтр каталога через ту же функцию `filterCatalogByAnswers()`, что использует и ручной каталог (не дублированная логика); (3) отфильтрованное подмножество (обычно 5-20 товаров, не весь каталог) уходит в Gemini с `responseSchema`, фиксирующей `{ bundles: [{ label, tier, items: [{productId, qty}], reasoning }] }`; (4) сервер валидирует, что каждый `productId` реально существует в отправленном подмножестве — невалидный bundle отбрасывается целиком; (5) если после валидации 0 bundle или API недоступен/таймаут (8с) — graceful fallback на чистый rule-based результат без AI-ранжирования (тот же паттерн, что уже валидирован в `useLivePrices()`). Gemini-клиент инкапсулирован в `api/_lib/ai/geminiClient.ts` — изоляция от вендора, миграция на OpenAI при необходимости не требует переписывать всю фичу.

**Как переиспользуется PDF-пайплайн.** Инлайновая логика `Calculator.tsx` (html2canvas → jsPDF, завязанная на локальный стейт компонента) не импортируется — вместо этого паттерн выносится в новый модуль `src/lib/pdf/renderSmetaPdf.ts` (10-строчный технический адаптер jsPDF/html2canvas), который использует новый `EquipmentPicker` со своим DOM-шаблоном. Заложена (но не обязательна к реализации сразу) архитектурная поддержка двух шаблонов: `renderConsumerSmeta()` (эмоциональный, для частника) и `renderTenderQuote()` (табличный, с реквизитами/НДС/сроком действия, для снабженца) — оба используют общий низкоуровневый адаптер.

**Смета явно разделяет "точную" и "ориентировочную" части на уровне данных** (не только текста UI): сумма `basePrice` товаров — точная, монтаж/кабель/HDD — ориентировочная (зависит от выезда специалиста). Это даёт UI и обоим PDF-шаблонам единый источник истины для формулировок вместо того, чтобы каждая поверхность решала это заново текстом.

## 5. Phases

### Фаза 0 — Каталог-фундамент
Модель данных `products` (Drizzle), простая admin-страница/сидинг-скрипт для ручного добавления товара, публичная страница каталога (список + карточка, без фасетных фильтров), 10-15 тестовых товаров вручную.

**Acceptance criteria:** таблица товаров в БД (мин. 10 позиций с фото/названием/характеристиками/ценой); каталог открывается корректно на мобильном и десктопе; добавление товара — понятные повторяемые шаги без правки кода; `Calculator.tsx` не затронут.

### Фаза 1 — Ручной подбор → корзина → смета → PDF (MVP главного пути)
Корзина (localStorage), пересчёт сметы через переиспользованную логику `pricing.ts` с разбивкой оборудование/работы, оговорка "цены ориентировочные" зафиксирована здесь как единый текст (переиспользуется дальше), генерация PDF по новому макету, минимальная точка входа на сайте (без финального дизайна), сбор контакта вместе со сметой.

**Acceptance criteria:** путь целиком проходим (каталог → корзина 2-3 товара → смета оборудование+монтаж → PDF); смета не расходится с логикой старого калькулятора; оговорка о примерности идентична в UI и PDF; нет оплаты/чекаута ни на одном экране; есть способ получить заявку (контакт) вместе со сметой.

> После этой фазы — точка остановки и сверки метрик, прежде чем продолжать (см. §7).

### Фаза 2 — Наполнение каталога до промо-объёма + процесс поддержания
Расширение каталога до 30-60 позиций по ключевым категориям, фиксация лёгкого процесса обновления (кто/как часто), опционально — договорённость с поставщиком о фиде.

**Acceptance criteria:** каталог закрывает 2-3 типовых сценария клиента без пустых категорий; зафиксирован ответ на "кто обновляет цены и как часто" (хотя бы как процесс, не обязательно код); нет "битых" карточек без фото/цены/характеристик.

> Явно отделена от AI-фазы: точность AI-рекомендаций напрямую зависит от качества каталога — запускать AI поверх "грязных" тестовых данных бессмысленно.

### Фаза 3 — AI-режим (Gemini) поверх готового каталога
Квиз из 4-6 наводящих вопросов (визуальные варианты ответа), `api/ai-recommend.ts` со structured output поверх rule-based префильтра, UI показа 2-3 наборов с ценой, выбор набора кладёт товары в общую корзину с возможностью донастройки, `GEMINI_API_KEY` как env-переменная.

**Acceptance criteria:** пользователь получает 2-3 набора из реально существующих товаров; набор редактируется в той же корзине, что и ручной выбор; при недоступности Gemini — понятный fallback на ручной каталог, не тупик; минимум 2-3 раунда ручного тестирования рекомендаций реальными людьми (не только разработчиком) с исправлением явных ошибок до релиза.
**Добавлено синтезом как обязательный AC (см. Tensions #1):** rate-limiting/anti-abuse на эндпоинте включён и проверен до публичного релиза фазы — это блокирующее требование security, не пункт бэклога "на потом".

### Фаза 4 — Редизайн главной страницы + tender-ready документ
Redesign Hero/боли/плюсы/блок "два входа в расчёт" в Linear-стиле с сохранением тактической айдентики, визуальное выравнивание остальных блоков без изменения их логики, сквозная проверка формулировки про примерность цены по всем поверхностям, доработка PDF под tender-формат — по факту реального B2B-фидбэка, если он к этому моменту есть.

**Acceptance criteria:** главная страница по новому порядку блоков, оба пути расчёта доступны и понятны с первого экрана; формулировки про примерность идентичны на Hero/боли/корзине/смете/PDF; danger-zone компоненты не регрессируют по известным багам (ручной прогон сценариев перед релизом).

## 6. Security plan (сжато)

**Threat model, по приоритету:**
1. Злоупотребление Gemini-эндпоинтом (спам/накрутка расходов на API) — вероятность и влияние высокие, публичный бесплатный-для-пользователя/платный-для-компании эндпоинт без лимита.
2. Prompt injection через свободный текстовый ввод в квизе + потенциальный XSS через нерендеренный как HTML ответ модели.
3. Накопление/утечка ПДн клиентов (контакты, адрес объекта) — новая фича не создаёт новую категорию ПДн относительно уже существующего `projects.address`/Telegram-заявок, но увеличивает объём точек сбора и добавляет третью сторону (Google Gemini), получающую данные через промпт, если туда попадут ПДн.
4. Секреты (`GEMINI_API_KEY`) — риск низкий при соблюдении уже принятого в проекте паттерна (`process.env` только внутри `api/`), но человеческий фактор в MVP-спешке — реальная точка отказа, закрывается на code review.
5. Скрапинг barlau.kz как источник нового каталога — уже вне объёма по брифу, зафиксировано как отдельный, более заметный (публичный каталог с фото/характеристиками) риск, если появится соблазн "по аналогии" с `equipment_prices`.
6. Доверие к AI-рекомендациям как репутационный (не строго технический) риск — несовместимый/несуществующий набор товаров в официальном КП снабженцу.

**Классификация данных.** Каталог и содержимое корзины — не ПДн. Имя/телефон/компания/адрес объекта в форме отправки КП — ПДн по закону РК. PDF, содержащий эти данные, наследует те же требования к хранению/доступу.

**Стратегия авторизации.** Каталог и корзина — без авторизации (публичный контент/клиентское состояние). Gemini-эндпоинт — без логина (иначе противоречит публичности лендинга), но обязателен anti-abuse: rate-limit по IP через простую таблицу в Neon, honeypot/лёгкая защита от ботов, лимит длины ввода, таймаут+fallback. PDF в Vercel Blob — не access control, а непредсказуемое имя файла (криптографически случайный компонент, не последовательный ID).

**Комплаенс.** Закон РК "О персональных данных" применим к телефону/имени/адресу через квиз/корзину/форму КП: явное согласие на обработку при отправке контактов, не хранить ПДн дольше необходимого, не передавать ПДн в промпт Gemini без нужды (развести шаг "подбор" от шага "контакты"), явно прописать в публичной политике конфиденциальности использование зарубежных провайдеров (Vercel/Neon/Google). NDA/конфиденциальность тендерных данных крупного клиента — организационный флаг для бизнеса, не техническая задача.

### Urgent-флаги (нельзя откладывать даже в MVP)
1. **Rate-limiting/anti-abuse на Gemini-эндпоинте обязателен уже в первой версии AI-режима** — нет безопасного пути "запустить сначала без этого"; риск = неожиданный счёт за API уже на первой неделе.
2. **`GEMINI_API_KEY` строго на сервере, вызов только из `api/`** — blocking-требование к самой первой реализации, не технический долг.
3. **Не передавать ПДн (телефон/имя/адрес) в промпт Gemini** — требование к архитектуре с первого коммита: развести "квиз про оборудование" (без ПДн) и "форма контактов" (с ПДн, через уже существующий Telegram-паттерн).

Всё остальное из бэклога security (валидация `productId`, непредсказуемые URL PDF, consent-чекбокс, единый источник правды для юридического текста, не рендерить ответ модели как HTML) — важно, но может добавляться итеративно в первые недели после запуска без критического окна риска.

## 7. Success metrics

**После фазы 1:** количество заявок/скачанных смет через новый путь vs старый калькулятор за одинаковый период (ориентир — "сравнимый объём", не "в 10 раз больше"); конверсия каталог → смета; доля брошенных корзин.

**После фазы 3:** соотношение выбора AI-режим vs ручной (прямой ответ на вопрос "нужен ли AI вообще"); доля AI-рекомендаций, которые пользователь донастраивает перед сметой (резкий перекос почти всегда — сигнал низкого доверия); качественная обратная связь от Павла/менеджеров ("похоже на то, что предложил бы я сам" vs "часто мимо").

**После фазы 4:** доля заявок от procurement-сегмента (по косвенным признакам — компания в контактных данных, запрос реквизитов); субъективная метрика Павла — тратит ли он/менеджеры меньше времени на "разговор с нуля" с клиентом, пришедшим со сметой.

**Сознательно не отслеживается на старте:** точная конверсия в продажу/выручку через новый путь — сделка всегда идёт через живого менеджера и выезд специалиста, это метрика продаж компании в целом, а не этой фичи, без CRM её нельзя корректно приписать одному источнику лида.

## 8. Risks (технические + доменные, по убыванию серьёзности)

1. **Наполнение и особенно поддержание каталога данными без фида от поставщика.** Системно недооценивается — не разовый ввод 30-60 товаров, а повторяющийся процесс (характеристики, фото, цены, снятие с производства) без которого каталог "протухает" за месяцы. Главный риск по срокам и доверию из всей фичи. *(research §7.1, PM фаза 2)*
2. **Rate-limiting на Gemini-эндпоинте отсутствует в первой версии.** Публичный + платный для компании эндпоинт без лимита = гарантированный риск неожиданного счёта, а не гипотетический. *(security, urgent-флаг #1)*
3. **Точность AI-рекомендаций на реальных, "грязных" данных каталога.** Первая версия промпта почти всегда даёт правдоподобные, но не всегда корректные рекомендации; доведение до уровня доверия procurement-аудитории требует нескольких раундов живого тестирования, которое трудно оценить одним числом заранее. *(research §7.2, architect §8.2, PM фаза 3 AC)*
4. **Сквозная юридическая согласованность формулировки "цены ориентировочные".** Требует согласованности между Hero/маркетинговыми блоками, UI корзины/сметы, текстом внутри PDF — рассинхрон формулировок это типичный источник репутационного/юридического риска, невидимый при дизайне одного экрана. Митигация заложена в данных (`EstimateResult` разделяет точную/ориентировочную часть), но контентная синхронизация — отдельная задача. *(research §4.2/7.3, architect §5.3, security §4)*
5. **html2canvas на многостраничных tender-ready документах.** Рендерит один `<canvas>` без разрывов страниц — риск обрезки/некорректного масштабирования при росте позиций в комплекте (30+ строк). Для MVP-объёма (5-15 строк) невысокий, но известная точка отказа при масштабировании PDF под procurement. *(research §3/§5, architect §8.2)*
6. **Накопление ПДн клиентов и предсказуемые URL PDF в Vercel Blob.** Растущий массив персональных данных без явного процесса хранения/удаления; публичный бакет с угадываемым URL потенциально раскрывает ФИО/телефон/адрес объекта в документе. *(security §1.3, §3)*
7. **Аддитивная правка `App.tsx` под опциональный `/katalog`-роут.** Danger-zone файл с историей багов (4 зафиксированных) — риск задеть существующие Clerk-гарды `/dashboard`/`/admin` или порядок роутов. Митигация: отдельный PR, ручной regression, либо отказ от роута в пользу модалки. *(architect §8.1)*
8. **Рассинхрон цены товара между добавлением в корзину и расчётом сметы** при персистентной localStorage-корзине и ручном редактировании `basePrice` в Drizzle Studio между визитами. Митигация уже заложена архитектурно (корзина хранит только `productId`+`qty`, цена всегда берётся из актуального каталога) — риск управляемый, не устранён полностью, но приемлем для "ориентировочной" сметы. *(architect §8.2)*
9. **`quotes.aiTranscript` как потенциально разрастающиеся данные.** Не блокер MVP, но стоит заложить (не обязательно реализовать сразу) политику ретенции. *(architect §8.2)*
10. **Двойная аудитория требует потенциально двух разных PDF-документов**, и попытка закрыть обе одним шаблоном не устроит ни одну полностью — архитектурно заложена возможность двух шаблонов, но решение о том, когда строить второй, зависит от реального B2B-фидбэка, который заранее не угадывается. *(research §4.3, architect §5.4, PM допущение 5)*

## 9. Tensions

Существенных прямых противоречий между документами немного — Architect, PM и Security в целом согласованы по ключевым решениям (AI как надстройка над rule-based, localStorage-корзина без авторизации, разделение точной/ориентировочной цены на уровне данных, разделение "подбора" и "сбора контактов" для защиты ПДн). Но нашлось два конкретных места трения, которые стоит явно зафиксировать, чтобы они не потерялись между фазами:

**1. Security считает rate-limiting на Gemini-эндпоинте блокирующим требованием к "первой версии AI-режима" — PM не включил это явно в acceptance criteria фазы 3.** PM-план фазы 3 фокусируется на точности рекомендаций, fallback при недоступности API и UX квиза — всё это правильно, но rate-limiting фигурирует только в architect.md (§4.3, как техническая деталь реализации) и security.md (как urgent-флаг), а не как явный, проверяемый пункт приёмки в pm.md. Риск — при обычном темпе разработки "фича готова" может означать "квиз работает и даёт рекомендации", а анти-абуз останется недоделанным до первого инцидента со счётом. **Решение синтеза:** rate-limiting добавлен как обязательный AC в фазу 3 выше (§5) — трактовать его как блокер релиза фазы 3, не как отдельный тикет "на потом".

**2. Architect предлагает опциональный `/katalog`-роут как ценное, но рискованное дополнение (SEO, шаринг ссылок для процурмента) — PM ни в одной фазе явно не берёт решение по нему на себя.** Architect честно закладывает этот пункт как "можно отказаться" и указывает конкретную митигацию (отдельный PR + regression на danger-zone `App.tsx`), но поскольку PM-фазы не упоминают роут вовсе, есть риск, что решение о нём будет принято ситуативно в процессе разработки фазы 0 или 4, без осознанной оценки риска/пользы и без предложенных архитектором мер предосторожности. **Решение синтеза:** вопрос вынесен в Clarifications (#5) как открытое решение, которое стоит явно принять (да/нет/отложить) до того, как кто-то реализует его "по пути".

За пределами этих двух пунктов ключевые открытые вопросы (нужен ли AI на MVP, как наполнять каталог, объём редизайна, формат "ориентировочных" цен, стыковка с barlau.kz-кэшем — все пункты из раздела "Известные напряжения" в BRIEF.md) оказались уже согласованно решены одинаково во всех трёх документах (PM фазирует AI на фазу 3 после готового каталога, architect технически это поддерживает, security подтверждает, что это снижает риск) — они вынесены в Clarifications как допущения, требующие подтверждения Павла, а не как расхождения между персонами.

## 10. Assumptions

1. Каталог на старте (фаза 0) наполняется вручную, 10-15 тестовых товаров, без парсинга и без готового фида от поставщика.
2. Поддержание каталога (фаза 2) — ручной процесс, ориентировочно раз в месяц, без выделенного контент-менеджера и без автоматизации на этом горизонте.
3. `GEMINI_API_KEY` будет получен и передан через переменные окружения Vercel к моменту начала фазы 3; ключ не обсуждается и не запрашивается в этом плане.
4. Целевой объём каталога для промо-запуска (фаза 2) — 30-60 позиций по 3-4 категориям (камеры, NVR, СКУД, базовые комплекты).
5. Требования снабженцев к tender-ready формату (реквизиты, НДС строкой, срок действия) уточняются по факту первого реального B2B-обращения, не проектируются заранее вслепую; до этого момента используется один PDF-документ для обеих аудиторий.
6. Редизайн главной (фаза 4) идёт после того, как функционал фаз 1-3 уже работает и проверен реальными заявками — визуал не блокирует запуск ценности; порядок фаз 3/4 можно поменять местами по решению Павла.
7. На старте нет выделенной аналитической системы для воронки нового пути — метрики фаз 1-4 первое время собираются вручную (подсчёт заявок/PDF в БД).
8. Отдельный `/katalog`-роут не реализуется на MVP — решение отложено до подтверждения ценности модалки (см. Clarifications #5).
9. Компания в РК, все провайдеры (Vercel/Neon/Google) зарубежные — трансграничная передача данных технически имеет место, но для масштаба компании не является блокером при условии прозрачной политики конфиденциальности на сайте.
10. AI-квиз собирает только параметры объекта (не ПДн) — контакты (имя/телефон/компания) собираются отдельно, на этапе "отправить КП", а не в промпте Gemini.

## 11. Out of scope (для первой версии)

- Онлайн-оплата/чекаут — оборудование не продаётся отдельно от монтажа (прямое ограничение брифа).
- Активация автообновления цен barlau.kz — отдельная, уже начатая ветка работы; не смешивать с новым каталогом.
- Изменение содержательной логики `Calculator.tsx` — остаётся вторым, второстепенным путём без изменений.
- Полноценная CMS для каталога с ролями/модерацией — ручной ввод/сидинг закрывает потребность при объёме в десятки товаров.
- Векторный поиск/ML-ранжирование рекомендаций — избыточно при каталоге 15-60 товаров, решается фильтрами + одним вызовом LLM.
- Открытый чат с AI-ассистентом вместо структурированного квиза — сознательное ограничение, снижает риск prompt injection.
- Сохранение корзины в БД с привязкой к Clerk-аккаунту — localStorage закрывает сценарий "посчитал и скачал за визит"; добавляется только по явному запросу пользователей.
- Мультиязычность каталога/сметы (казахский/английский) — не поднято ни в брифе, ни в концепте; отдельная фаза после подтверждения ценности русскоязычной версии.
- Серверный рендеринг PDF (Puppeteer/React-PDF) вместо html2canvas — точечная доработка только если tender-ready документ реально упрётся в ограничения html2canvas.
- WAF, полноценная CAPTCHA, SIEM/аудит-логирование, формальная DPIA, отдельный privacy-офицер, шифрование PDF на уровне хранилища, SOC2-подобные процессы — избыточны для масштаба компании (явно зафиксировано security).

## 12. Branch naming (GIT-OS)

Формат GIT-OS: `feat/<name>` от `<target>` (вероятно `main`), стек снизу вверх при зависимых PR. Фаза 0 и фаза 1 логически последовательны (каталог → корзина/смета/PDF поверх него) и по правилу "макс. 5-6 файлов на PR" каждая фаза почти наверняка потребует нескольких PR — стекуем их:

- **Фаза 0 (каталог-фундамент):** `feat/equipment-catalog-foundation`
  - при необходимости разбить на стек: `feat/equipment-catalog-schema` → `feat/equipment-catalog-page` (второй ветвится от первого)
- **Фаза 1 (ручной подбор → корзина → смета → PDF):** `feat/equipment-cart-estimate`, ветвится от `feat/equipment-catalog-foundation`, таргет — та же ветка (стек), либо `main`, если фаза 0 уже смержена к моменту старта фазы 1
  - при разбиении: `feat/equipment-cart` → `feat/equipment-estimate-pdf`

Порядок мержа: `feat/equipment-catalog-foundation` → `main`, затем `feat/equipment-cart-estimate` → `main`. Fix-ветки в процессе — `fix/<name>` от той же цели, что и затронутый feature-branch.
