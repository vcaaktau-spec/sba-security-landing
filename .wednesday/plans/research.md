> Этап Research в цепочке greenfield-планирования. Это доменное исследование для Architect/PM/Security агентов — не архитектура и не фичи. Основа: `BRIEF.md`, `docs/CONCEPT-2026.md`, `.wednesday/codebase/MASTER.md`, беглый просмотр `src/components/Calculator.tsx` и `src/db/schema.ts`.

## Контекст текущей кодовой базы (для калибровки, не для решений)

- Стек подтверждён: React + Vite + Tailwind/shadcn, Clerk, Neon Postgres + Drizzle, Vercel serverless `api/`.
- В `src/db/schema.ts` уже есть три таблицы: `projects` (кейсы клиентов), `documents`, и **`equipment_prices`** — плоский кэш цен по ключам (`camera.2MP`, `nvr.8`, `poe.16`, `hdd.4`), спарсенных с barlau.kz, сейчас неактивный, используется только как overlay поверх `DEFAULT_PRICES` в `src/lib/pricing.ts`. Это НЕ каталог товаров — это ценовые тиры для старого калькулятора. Новый каталог (конкретные SKU с фото/характеристиками) — отдельная сущность, которой в схеме пока нет.
- `Calculator.tsx` уже умеет: пошаговый квиз → расчёт по тирам (камеры/разрешение/кабель/HDD/монтаж) → вероятно PDF-экспорт (jsPDF+html2canvas, судя по брифу) и `useLivePrices()` хук с graceful fallback на дефолтные цены при недоступности `/api/prices`.
- `MASTER.md` отмечает `Calculator.tsx`, `App.tsx`, `Hero.tsx`, `Footer.tsx`, `Projects.tsx`, `Testimonials.tsx` как "danger zones" (частые баг-фиксы) — редизайн главной и переиспользование PDF-паттерна нужно делать с осторожностью, это не чистый лист.

## 1. Существующие решения на рынке

Рынок сайтов охранных/CCTV-компаний делится на два полюса, и оба слабы именно в том месте, которое просит бриф.

**Полюс А — дистрибьюторы/производители (Lorex Pro, CCTV Camera World, eLine Technology, Eclipse CCTV, Optiview, Blackwire)**: у них есть полноценный e-commerce каталог с фильтрами (разрешение, дальность ИК, PoE/Wi-Fi, indoor/outdoor), но:
- Это классические каталоги "выбери сам по фильтрам" — почти никто не предлагает наводящий диалог/квиз, который переводит "у меня склад 500 м², нужна ночная съёмка" в конкретный список товаров. Подбор — задача пользователя, не сайта.
- Заточены под самостоятельную покупку и самостоятельный монтаж (DIY-сегмент), у части есть "pro"/"wholesale"-раздел с B2B-ценами по логину — но это отдельная ветка, не единый флоу с розницей.
- Конфигураторы "система под ключ" (например, у некоторых производителей NVR-китов) обычно жёстко привязаны к готовым бандлам вендора, а не к гибкой комбинации SKU + расчёту монтажа.

**Полюс Б — локальные монтажные компании (Казахстан/СНГ, включая barlau.kz, sonet.kz и подобные)**: у них есть сильная сторона SBA — экспертиза монтажа и присутствие на месте, — но сайты почти всегда:
- Либо статичный список услуг с ценой "от" и формой "оставить заявку", либо простой калькулятор по абстрактным тирам (как нынешний `Calculator.tsx`) без привязки к реальным товарам.
- Каталог оборудования, если есть, — это просто прайс-лист/карточки товаров без интерактивного подбора и без корзины, соединённой со сметой на монтаж.
- Официальный B2B-формат КП (для тендеров/закупок) почти никогда не автоматизирован — снабженец получает то же самое, что и частник: письмо/PDF на коленке или разговор с менеджером.

**Вывод для домена**: связка "квиз/AI-подбор → каталог SKU → корзина → смета с монтажом → tender-ready PDF" в этой нише практически не встречается ни у дистрибьюторов (у них нет монтажной сметы и tender-формата), ни у локальных монтажников (у них нет каталога и подбора). Это реальная ниша дифференциации, а не пересборка чужого паттерна — значит референсов "скопировать один в один" в CCTV-вертикали нет; ближайшие рабочие аналогии стоит брать из смежных B2B-конфигураторов (солнечные панели, климатическое оборудование, промышленное оборудование под заказ — там подбор по параметрам объекта → комплект → КП является стандартным паттерном).

Источники: [CCTV distributors directory](https://www.securityinformed.com/companies/cctv-distributors/directory.html), [Lorex Pro](https://pro.lorex.com/), [CCTV Camera World Wholesale](https://www.cctvcameraworld.com/security-camera-wholesale-dealer.html), [eLine Technology](https://www.elinetechnology.com/wholesale-security-cameras/), [Blackwire](https://www.blackwiredesigns.com/filters/product_brand/ring/product_cat/cctv-security/), [sonet.kz — проектирование СКС](https://sonet.kz/proektirovanie-sistem-videonablyudeniya/).

## 2. Стандартный/современный стек поверх React/Vite/Vercel/Neon-Drizzle

Что здесь **не нужно изобретать заново** — для каждого куска фичи есть устоявшийся паттерн, укладывающийся в уже выбранный стек:

- **Каталог товаров в Postgres/Drizzle**: обычная реляционная модель `products` + `categories` + `product_specs` (либо jsonb-поле характеристик, как уже сделано для `equipment` в `projects` — в кодовой базе есть прецедент jsonb-массивов/объектов). Полнотекстовый/фасетный поиск по 15-100 товарам не требует Algolia/Elastic — хватает Postgres `ILIKE`/GIN-индекса по jsonb, это стандартно для каталогов такого масштаба.
- **Корзина без чекаута**: клиентское состояние — стандартно через Zustand/Jotai или просто React Context + `localStorage`/`sessionStorage` persist (паттерн "shopping cart без оплаты" отработан миллион раз в B2B quote-builder продуктах). Синхронизация между визитами через БД нужна только если есть аутентификация пользователя (Clerk уже есть в проекте) — иначе localStorage полностью закрывает сценарий "посчитал и скачал/отправил".
- **Расчёт сметы**: чистая функция на клиенте или serverless-эндпоинте, переиспользующая существующую ценовую логику монтажа/кабеля/HDD из `src/lib/pricing.ts` — стандартный подход "чистая функция трансформации корзины в смету", ничего экзотического.
- **AI-рекомендации через Gemini**: Google Gemini API поддерживает нативный **structured output** (`responseSchema`/`responseMimeType: application/json`, включая enum и упорядоченные свойства) — то есть можно напрямую попросить модель вернуть JSON со списком `productId`/`qty`/`reason` без хрупкого парсинга свободного текста. Это стандартный, задокументированный путь на 2026 год, отдельная function-calling обвязка не обязательна, если формат ответа заранее известен и фиксирован (что здесь и есть — набор из каталога). Вызов — из serverless-функции в `api/` (не с клиента, ключ не должен быть в браузере) — это ровно то, что уже предусмотрено в брифе.
- **Генерация PDF/КП**: jsPDF + html2canvas уже есть и работает для старого калькулятора — переиспользование паттерна для нового макета корзины полностью стандартно и не требует новой библиотеки. Из современных JS PDF-библиотек 2026 года (обзоры Nutrient/Apryse/Joyfill) альтернативы (Puppeteer/headless Chrome на сервере, pdf-lib, React-PDF, Playwright PDF) дают более качественную типографику и предсказуемую вёрстку многостраничных документов, но требуют серверного рендеринга — это апгрейд, а не необходимость для MVP.
- **Environment/секреты**: `GEMINI_API_KEY` как переменная окружения Vercel — стандартная практика, уже заложена в бриф правильно.

Источники: [Gemini API structured outputs](https://ai.google.dev/gemini-api/docs/structured-output), [Google: JSON Schema + property ordering support](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-structured-outputs/), [Top JS PDF libraries 2026 — Nutrient](https://www.nutrient.io/blog/top-js-pdf-libraries/), [JS PDF generation methods — Nutrient](https://www.nutrient.io/blog/generate-pdfs-from-javascript/), [PDF template generation libraries 2026 — Apryse](https://apryse.com/blog/pdf-template-generation-libraries).

## 3. Чего стоит избегать здесь и почему

- **Полноценный e-commerce чекаут/оплата** — прямо исключено брифом ("оборудование не продаётся отдельно от монтажа"), но стоит явно предостеречь: не тянуть за собой типичные e-commerce паттерны (управление остатками/stock, платёжные интеграции, статусы заказов) — это не тот продукт, и добавление "на всякий случай" утроит объём без пользы.
- **Полноценная поисковая/рекомендательная ML-инфраструктура** (векторные БД, embeddings-пайплайны, ML-модели ранжирования) — при каталоге в 15-100 товаров это explicit overkill; задача решается либо rule-based фильтрацией, либо одним вызовом LLM с полным каталогом в контексте (см. п.5) — не нужно строить infra уровня Amazon.
- **Автоматизированный скрапинг/парсинг barlau.kz как источник каталога "по умолчанию"** — юридически и технически шатко (нет машиночитаемого фида, публичные цены без логина = скрапинг чужого прайса конкурента/поставщика для собственного публичного каталога — репутационный и потенциально договорной риск, если barlau.kz — партнёр-поставщик, а не открытые данные). Это уже отдельно помечено в брифе как "вне объёма", но важно не тянуть эту практику неявно и в новый каталог тоже.
- **Хранение AI-переписки/истории диалога как "чат"-интерфейс общего назначения** — Gemini-режим в брифе явно структурный (вопросы → JSON-рекомендация), не открытый чат. Соблазн сделать "чат с ассистентом" вместо "мастера из N вопросов" добавит объём (модерация свободного ввода, prompt injection через пользовательский текст, непредсказуемые ответы) без выигрыша для сценария подбора оборудования.
- **Жёсткая привязка PDF-макета к html2canvas-рендерингу сложных многостраничных таблиц** — html2canvas хорош для одностраничных карточек (как, видимо, в старом калькуляторе), но плохо масштабируется на официальные многостраничные КП с таблицами позиций, разрывами страниц, колонтитулами — это источник скрытых багов при росте числа позиций в корзине (см. раздел 7).
- **Кастомный auth/сессии для сохранения корзины** — Clerk уже в проекте, не нужно городить отдельный механизм "гостевых аккаунтов" для персистентности корзины, если localStorage закрывает сценарий.

## 4. Неочевидные сложности домена

**4.1 Наполнение каталога без машиночитаемого фида**
У barlau.kz нет экспорта — только карточки товаров с ценой без логина. Реалистичные варианты: (а) ручной ввод силами Павла на 10-15 тестовых товарах для старта (уже предложено в CONCEPT-2026.md), (б) точечный, разовый (не автоматизированный/не постоянный скрапинг) сбор данных по карточкам для затравки каталога — юридически всё равно требует осторожности и явного разрешения/партнёрства с поставщиком, (в) получение прайс-листа/фида напрямую от поставщика по договорённости — самый чистый путь, но зависит от готовности партнёра. Ключевая скрытая проблема — не единоразовое наполнение, а **поддержание**: цены на CCTV-оборудование в Казахстане меняются (курс тенге, поставки), фото/характеристики устаревают, товары снимаются с производства — без процесса обновления каталог "протухнет" за месяцы, а не годы.

**4.2 Юридический/доверийный риск "примерных" цен**
В РК есть развитая практика публичной оферты (ГК РК регулирует дистанционную продажу товаров) — но здесь ключевое отличие: **оборудование не продаётся само по себе**, только с монтажом, и на сайте явно должна стоять оговорка "цены ориентировочные, точная стоимость — после выезда специалиста" (это уже заложено в бриф). Это снижает риск трактовки цены как публичной оферты на конкретных условиях (по общей практике, публичная оферта требует определённости существенных условий — а "ориентировочная" формулировка эту определённость сознательно снимает). Тем не менее есть подводные камни: (а) формулировка должна быть юридически последовательной по всему сайту, а не только в корзине — если Hero/маркетинговые блоки обещают "точный расчёт онлайн", а мелким текстом внизу написано "ориентировочно", это создаёт основания для претензии о введении в заблуждение по законодательству о защите прав потребителей; (б) для монтажных работ ситуация иная — сметная стоимость работ без выезда специалиста объективно менее предсказуема, чем цена конкретного SKU оборудования (она известна точно), и текст оговорки должен различать эти два случая, а не смешивать их в одну общую фразу; (в) генерируемый PDF/КП сам по себе как исходящий документ компании должен содержать те же оговорки, что и веб-интерфейс — не только UI, но и артефакт, который клиент/снабженец пересылает дальше по цепочке согласования.

**4.3 Двойная аудитория: частники vs procurement**
У крупных казахстанских компаний закупка через снабженца часто идёт по внутренним процедурам, ориентированным на логику госзакупок РК (запрос ценовых предложений/ЗЦП, тендерная документация) даже если сама компания частная — то есть снабженец психологически ждёт документ, похожий на официальное КП: реквизиты компании (БИН, юр. адрес, банковские реквизиты), сроки действия предложения, спецификацию позиций с артикулами, подпись/печать (или место под неё), НДС отдельной строкой. Обычный "чек из корзины" интернет-магазина этому не соответствует. Скрытая сложность — не в дизайне PDF, а в том, что **два разных документа могут быть нужны одновременно**: маркетинговое "предложение" для частника (эмоциональное, с фото, преимуществами) и формальное "коммерческое предложение" для снабженца (сухое, табличное, с реквизитами) — если попытаться закрыть оба одним шаблоном, результат не устроит ни одну из аудиторий полностью. Это прямая точка входа для Tensions-раздела PM-агента.

Источники: [Публичная оферта в Казахстане — ГК РК](https://blog.trustme.kz/publichnaya-oferta-kazakhstan-kak-sostavit/), [Как закупать видеонаблюдение и пожарную сигнализацию — МЦФЭР](https://gz.mcfr.kz/article/1429-kak-zakupat-videonablyudenie-i-pojarnuyu-signalizatsiyu), [Ценовое предложение в госзакупках РК, образец — МЦФЭР](https://gz.mcfr.kz/article/183-tsenovoe-predlojenie-v-goszakupkah-ponyatie-obrazets-zapros), [Коммерческое предложение в госзакупках — Тендербот](https://tenderbot.kz/blog/post/kommercheskoe-predlozhenie-v-goszakupkakh-chto-nuzhno-znat).

## 5. Интеграционный ландшафт

**Google Gemini API**
- Поддерживает structured output "из коробки": параметр `responseSchema` (JSON Schema-совместимый, с упорядочиванием свойств) заставляет модель вернуть валидный JSON без ручного парсинга markdown/текста. Для сценария "дай 2-3 набора товаров из каталога X по ответам пользователя Y" это прямое попадание — схема ответа фиксирует `{ bundles: [{ label, items: [{productId, qty}], reasoning }] }`.
- Function calling (отдельный механизм, где модель "вызывает" объявленные функции) здесь избыточен — он нужен, когда модели требуется многошаговое взаимодействие с внешними системами в процессе рассуждения (поиск, вычисления). Здесь весь каталог разумного размера (15-100 позиций) можно передать целиком в промпт вместе с ответами квиза за один вызов — structured output проще, дешевле по латентности и предсказуемее, чем оркестрация function-calling.
- Практическое ограничение: точность рекомендации Gemini прямо зависит от качества и полноты данных каталога, переданных в промпт (характеристики, цена, назначение) — "мусор на входе — мусор на выходе" здесь острее, чем где-либо (см. раздел 7).

**Аналоги**
- OpenAI Structured Outputs / `response_format: json_schema` — концептуально идентичный механизм, взаимозаменяем на уровне архитектуры (если Gemini окажется недоступен/дорог в Казахстане по каким-то причинам, миграция на OpenAI — это замена одного serverless-эндпоинта, не переписывание фичи). Прямых указаний в брифе на необходимость такой гибкости нет, но стоит проектировать AI-эндпоинт с тонкой изоляцией от конкретного вендора.
- Локальные/self-hosted LLM — избыточны для объёма задачи (структурированная рекомендация по небольшому каталогу), добавляют операционную сложность без выигрыша.

**PDF на клиенте**
- jsPDF + html2canvas уже есть и работает — переиспользование оправдано для MVP. Для более сложных многостраничных tender-ready документов (см. 4.3) в будущем стоит рассмотреть серверный рендеринг (Puppeteer/Playwright в serverless-функции, либо React-PDF) — но это решение архитектора, не задача этого исследования.

**Когда AI-рекомендатель вообще оправдан против rule-based подбора**
Это ключевой вопрос для Tensions (уже отмечен в брифе как открытый). Домен-аргументы за и против:
- *За rule-based (простые правила/decision tree по ответам квиза → фильтр каталога по тегам)*: предсказуемость (нет риска, что модель порекомендует несочетаемые позиции — например, IP-камеру с аналоговым регистратором), нулевая стоимость и латентность вызова, не требует ключа/аптайма стороннего API, полностью тестируемо (юнит-тесты на комбинации ответов). При каталоге 15-100 товаров с чёткими тегами (indoor/outdoor, разрешение, ночная съёмка, дальность, тип подключения) rule-based способен закрыть 80-90% сценариев подбора не хуже LLM.
- *За AI-рекомендатель*: ценность появляется там, где входные требования пользователя нечёткие/текстовые ("хочу видеть номера машин на въезде ночью с 30 метров") и нужно смэтчить это с техническими характеристиками каталога — то, что сложно закодировать как чистое правило без роста дерева решений до нечитаемого состояния. Также AI даёт естественный текст-обоснование ("рекомендуем эту камеру, потому что..."), что rule-based требует писать вручную для каждой комбинации.
- *Практический вывод для домена*: AI-режим оправдан как **надстройка поверх той же rule-based фильтрации**, а не как замена — модель должна получать уже отфильтрованное по жёстким ограничениям подмножество каталога (не весь каталог целиком без проверки совместимости), и её роль — ранжирование/формулировка/группировка в наборы, а не свободный выбор произвольных SKU. Это снижает риск галлюцинаций (рекомендация несуществующего товара) и несовместимых комплектов. Финальное решение по объёму MVP (нужен ли AI-режим на старте vs можно ли обойтись только rule-based+вручную) брифом уже вынесено в Tensions — это исследование лишь даёт данные для этого решения, не принимает его.

Источники: [Gemini structured outputs](https://ai.google.dev/gemini-api/docs/structured-output), [Firebase AI Logic — structured output](https://firebase.google.com/docs/ai-logic/generate-structured-output), [Rule-based vs AI recommendation — Boost Commerce](https://blog.boostcommerce.net/posts/rule-based-ai-powered-recommendation), [AI recommendation engine dev guide — Brocoders](https://brocoders.com/blog/ai-recommendation-matching-engine-development/).

## 6. Реалистичные сроки (небольшая команда/один разработчик)

Ориентир — не оценка конкретных задач (это работа архитектора/PM), а порядок величины по аналогичным проектам такого масштаба (каталог + AI-подбор + частичный редизайн лендинга поверх существующей кодовой базы, не greenfield):

- **Каталог (модель данных + CRUD/наполнение + страница каталога)**: обычно 1-2 недели инженерной работы на код при готовой схеме — но фактический срок определяется не кодом, а темпом наполнения данными (см. раздел 7), который у одного человека без фида от поставщика реалистично растягивается на недели, параллельно остальной разработке.
- **Корзина + пересчёт сметы + PDF под новый макет**: 1-1.5 недели при переиспользовании существующего PDF-паттерна и ценовой логики; больше, если многостраничный tender-ready формат потребует серверного рендеринга вместо html2canvas.
- **Gemini-интеграция (эндпоинт + структурированный вывод + UI квиза)**: 3-5 дней на "happy path" с готовым каталогом; плюс отдельный, отдельно недооцениваемый бюджет времени на итерации точности рекомендаций после первых реальных тестов (обычно требует 2-3 раунда доработки промпта/фильтрации после того, как каталог наполнен реальными, а не тестовыми товарами).
- **Редизайн главной страницы в Linear-стиле** (Hero, боли, преимущества, два входа в расчёт) с сохранением текущей тактической айдентики: 1.5-2.5 недели в зависимости от того, делается ли весь объём за один заход или по частям (сам бриф отмечает это как открытый вопрос) — учитывая, что затрагиваемые компоненты (`Hero.tsx`, `Footer.tsx`, `Statistics.tsx`, `Testimonials.tsx`, `Projects.tsx`) отмечены в MASTER.md как "danger zones" с историей багов, что обычно замедляет правки на 20-30% против "чистых" компонентов.

**Итоговый грубый диапазон для всей фичи целиком** (для одного опытного full-stack разработчика, без учёта параллельного наполнения каталога данными как блокера) — порядка **5-8 календарных недель** при последовательной разработке по порядку, предложенному в CONCEPT-2026.md (каталог → корзина/смета/PDF → AI → редизайн → полировка). Это оценка порядка величины для калибровки Tensions/roadmap, не обязательство — точный план и разбивку на этапы делает архитектор/PM.

## 7. Скрытая сложность — что обычно занимает в 3 раза дольше, чем кажется

1. **Наполнение и поддержание каталога данными.** Это системно недооценивается везде, не только здесь: "добавить 30 товаров" звучит как день работы, но на практике включает — поиск достоверных характеристик (разрешение, угол обзора, дальность ИК, IP-класс защиты) из разрозненных источников (сайты производителей на английском/китайском, datasheet PDF), подбор/лицензирование фотографий товара, перевод/адаптацию описаний под целевую аудиторию, проверку актуальности цены на момент публикации, и — самое дорогое по времени — **повторение этого процесса каждый раз, когда товар снимается с производства или меняется цена**. Без выделенного процесса (кто, как часто, по какому чек-листу обновляет каталог) 15-30 товаров, наполненных за первую неделю, к третьему месяцу содержат устаревшие цены и "битые" фото — именно это тянет доверие процурмент-аудитории вниз сильнее всего.
2. **Точность AI-рекомендаций.** Первая версия промпта почти всегда даёт правдоподобные, но не всегда корректные рекомендации на реальных, "грязных" данных каталога (в отличие от чистых тестовых 10-15 позиций, на которых обычно ведётся разработка) — несовместимые комбинации (аналоговая камера + IP-регистратор), рекомендации не в наличии, наборы, не укладывающиеся в разумный бюджет. Доведение до состояния "рекомендации внушают доверие процурмент-аудитории" обычно требует нескольких раундов реального тестирования с живыми пользователями/менеджерами SBA, а не только с разработчиком — это итеративный процесс, который трудно оценить одним числом на старте.
3. **Юридические формулировки про "примерные цены".** Кажется задачей на один абзац текста, но по факту требует согласованности между несколькими независимыми поверхностями — маркетинговыми блоками на главной (Hero/боли/преимущества не должны противоречить оговорке в корзине), UI корзины/сметы, текстом внутри сгенерированного PDF, и, если решение примет архитектор, отдельно между "ценой оборудования" (относительно точной) и "стоимостью монтажа" (объективно ориентировочной, зависит от выезда). Рассинхрон формулировок между этими поверхностями — типичный источник репутационного/юридического риска, который не виден на этапе дизайна одного экрана, а всплывает только при сквозной проверке всего пользовательского пути.
4. **(Дополнительно, но по той же логике) tender-ready документ для procurement.** Требования снабженца (реквизиты компании, НДС строкой, срок действия предложения, формат таблицы позиций) обычно выясняются только после первой реальной попытки использовать сгенерированный PDF в закупке крупного клиента — то есть первая версия документа почти гарантированно потребует доработки по фидбэку от реального B2B-клиента, а не угадывается полностью заранее.

## 8. Паттерны успеха в нише (конфигураторы, B2B quote-builders, self-serve procurement)

Общие паттерны, которые устойчиво работают в смежных B2B-конфигураторных продуктах (солнечные панели, промышленное/инженерное оборудование, климатика, IT-инфраструктура под заказ) и применимы к CCTV-домену:

- **Прогрессивное раскрытие сложности**: короткий квиз из 4-6 наводящих вопросов (не 15-20) с понятными, визуальными вариантами ответа (иконки "улица/помещение/периметр", а не текстовые дропдауны) — снижает отток на старте и работает одинаково хорошо для обеих аудиторий.
- **"Показать N вариантов, не один"**: успешные конфигураторы почти всегда предлагают 2-3 готовых набора (эконом/оптимум/премиум или похожий фрейминг) вместо единственной "правильной" рекомендации — это ровно то, что уже заложено в бриф ("2-3 конкретных набора на выбор"), и это совпадение с лучшей практикой стоит явно подтвердить архитектору/PM как валидированное решение, а не рискованный выбор.
- **Прозрачность состава набора**: пользователь должен видеть, из чего состоит рекомендованный набор и мочь заменить/убрать отдельную позицию, не начиная подбор заново — то есть AI-набор должен "приземляться" в ту же корзину, что и ручной выбор, с полным контролем после этого (это тоже уже заложено в брифе через единую корзину).
- **Разделение "интереса" и "обязательства"**: успешные self-serve procurement flows явно не просят оплату/оформление на этапе конфигурации — только сбор контактов/скачивание КП, оставляя финальную сделку живому менеджеру (созвучно ограничению брифа "без чекаута").
- **Официальный документ как самостоятельная ценность**: в B2B quote-builder продуктах скачиваемое/отправляемое КП само по себе является точкой конверсии (снабженец должен показать документ внутри компании для согласования) — то есть качество и убедительность PDF имеет вес, сопоставимый с качеством самого подбора товаров, и не должно рассматриваться как второстепенный "экспорт в конце".
- **Явные, но не пугающие дисклеймеры о точности цены** — паттерн "цена по конфигурации ≈ ориентир, финал после консультации/замера" стандартен в нишах, где итоговая цена зависит от выезда на объект (солнечные панели, окна, климатика) — SBA не изобретает здесь новый UX-паттерн, а следует уже привычному пользователю сценарию, что снижает риск недоверия при условии последовательной формулировки (см. раздел 4.2/7.3).

Три главные скрытые ловушки, которые почти гарантированно недооценены в брифе: (1) наполнение и особенно поддержание каталога данными без фида от поставщика, (2) доведение точности AI-рекомендаций до уровня, приемлемого для procurement-аудитории, требующее нескольких раундов реального тестирования, и (3) сквозная согласованность юридических формулировок про "ориентировочные" цены по всем поверхностям сайта и PDF, а не только в одном месте корзины.
