## 1. System design overview

### 1.1 Где физически живёт фича

Текущая точка входа — `src/pages/Home.tsx`: рендерит секции лендинга подряд и управляет одним модальным окном (`isCalcOpen` → `<Calculator onClose={...} />`) поверх `AnimatePresence`. Это уже готовый, проверенный паттерн "секция на главной открывает full-screen модалку поверх Home" — им и стоит воспользоваться для нового пути, а не изобретать отдельный полноэкранный роут.

Предлагаемое встраивание:

- В `Home.tsx` добавляется **второе модальное состояние** (`isPickerOpen`) по тому же паттерну, что и `isCalcOpen` — отдельный, независимый флаг, не переиспользующий состояние калькулятора. Открывается из нового блока "Два пути расчёта" (часть редизайна Hero/секций — зона ответственности PM/дизайна), а также из Hero/Footer CTA рядом с существующей кнопкой "Быстро посчитать монтаж" (которая продолжает открывать старый `Calculator`).
- Новый компонент — `src/components/EquipmentPicker/` (директория, не один файл — фича заведомо больше одного экрана): `EquipmentPicker.tsx` как оболочка с внутренними шагами `mode-select → (ai-quiz | catalog) → cart → estimate/pdf`. Внутреннее состояние шага (`"mode" | "quiz" | "catalog" | "cart"`) живёт в самом компоненте, аналогично `step` в `Calculator.tsx`, но это **отдельный компонент**, не разросшийся `Calculator.tsx`.
- **Опционально** отдельный роут `/katalog` (полноценная страница каталога, не только модалка) — обоснование: у процурмент-аудитории и в тендерной практике часто нужна расшариваемая ссылка на позицию/раздел каталога, и SEO-выгода от индексируемых страниц товаров (в отличие от модалки на SPA-роуте). Это единственное место, где архитектура **обязана** тронуть `src/App.tsx` (danger zone, 4 бага в истории) — правка чисто аддитивная (добавить один `<Route>`), без изменения существующей логики роутинга/Clerk-гардов. Рекомендация: делать этот роут отдельным PR/шагом, с ручной regression-проверкой существующих роутов после мержа, именно из-за статуса danger zone. Если объём MVP урезается — реализовать без нового роута (только модалка), но не удалять этот пункт из бэклога.

```
Home.tsx
 ├─ Hero (CTA "Подобрать оборудование" + CTA "Быстрый расчёт монтажа")
 ├─ ... существующие секции ...
 ├─ Footer (дублирующие CTA)
 ├─ [modal] Calculator            — как сейчас, БЕЗ ИЗМЕНЕНИЙ
 └─ [modal] EquipmentPicker (new) — mode-select → quiz(AI) | catalog → cart → estimate → PDF

(опционально) /katalog route → CatalogPage.tsx → тот же EquipmentPicker в "каталог"-режиме,
             но как полноценная страница, с deep-link на категорию/товар
```

### 1.2 Переиспользование PDF-пайплайна

`Calculator.tsx` генерирует PDF инлайново: скрытый DOM-шаблон (`smetaRef`) → `html2canvas` → `jsPDF`. Логика встроена прямо в компонент и завязана на его локальный стейт (`objectNames`, `poeSummary` и т.д.) — **эту функцию нельзя импортировать**, не трогая `Calculator.tsx`.

Архитектурное решение: вынести **паттерн**, а не код, в новый переиспользуемый модуль `src/lib/pdf/renderSmetaPdf.ts`:

```ts
// src/lib/pdf/renderSmetaPdf.ts
export async function renderSmetaPdf(node: HTMLElement, filename: string): Promise<void> {
  const [{ default: jsPDF }, { default: html2canvas }] = await Promise.all([
    import("jspdf"),
    import("html2canvas"),
  ]);
  const canvas = await html2canvas(node, { scale: 2, backgroundColor: "#ffffff", useCORS: true });
  const imgData = canvas.toDataURL("image/png");
  const pdf = new jsPDF({ unit: "px", format: [canvas.width, canvas.height] });
  pdf.addImage(imgData, "PNG", 0, 0, canvas.width, canvas.height);
  pdf.save(filename);
}
```

`Calculator.tsx` продолжает использовать свою инлайновую копию (не трогаем). Новый `EquipmentPicker` использует `renderSmetaPdf()` с собственным DOM-шаблоном (см. §5.4 про два типа документа — маркетинговый и tender-ready). Это не дублирование логики бизнес-правил — дублируется только 10-строчный технический адаптер jsPDF/html2canvas, что осознанно дешевле, чем рефакторить danger-zone компонент ради DRY.

### 1.3 Переиспользование ценовой логики монтажа

`src/lib/pricing.ts` уже общий модуль (не компонент, не danger zone) — `DEFAULT_PRICES`, `HDD_RATES`, `getHddCost()`, `mergePrices()`, `useLivePrices` живут отдельно от `Calculator.tsx` за одним исключением: хук `useLivePrices()` физически определён **внутри** `Calculator.tsx` (строки 22–41), а не в `pricing.ts`. Для новой фичи его нужно **скопировать** в `src/lib/pricing.ts` (или в новый `src/hooks/useLivePrices.ts`) как экспортируемую функцию — это чисто техническое перемещение общего кода в общее место, не изменение поведения `Calculator.tsx` (он продолжит работать, просто будет использовать тот же хук из общего модуля вместо локальной копии, либо останется на своей копии, если даже это трогать нежелательно — тогда `EquipmentPicker` заводит собственный идентичный хук). Рекомендация архитектора: **дублировать хук, не трогать `Calculator.tsx` вообще** — 15 строк дублирования безопаснее одной лишней правки в danger-zone файле с 2 багфиксами в истории.

## 2. Модель данных (Drizzle)

### 2.1 Принцип: `equipment_prices` не трогаем и не путаем с каталогом

`equipment_prices` — плоский **ценовой кэш по абстрактным тирам** (`camera.2MP`, `nvr.8`...) для старого калькулятора. Новый каталог — это **конкретные SKU** с фото и характеристиками для витрины/подбора. Смысл принципиально разный: один описывает "тип позиции для формулы", другой — "товар, который можно положить в корзину". Их не объединяем, но продукт каталога может **опционально** нести `priceTierKey`, ссылающийся на `equipment_prices.key`, — см. §2.3.

### 2.2 Новые таблицы

`categories` отдельной таблицей сознательно **не заводим** на MVP — `productCategoryEnum` из 8 значений достаточен при каталоге 15–100 товаров (см. research §3 про переинженерию), и enum проще администрировать через Drizzle Studio, чем отдельную таблицу-справочник с CRUD. Если каталог вырастет за пределы enum (нужны подкатегории/иерархия) — миграция на `categories`-таблицу тривиальна и не блокирует MVP.

### 2.3 Связь с `projects`

Прямой FK от `quotes`/`products` к `projects` не нужен — `projects` описывает уже смонтированные объекты для клиентского портфолио/Dashboard, это другой bounded context (см. §5). Если в будущем понадобится "конвертировать выигранный quote в project" — это ручной процесс менеджера, не архитектурная связь на уровне схемы.

## 3. Корзина: клиентское состояние vs персистентность

**Решение: localStorage, без БД, без обязательной привязки к Clerk-аккаунту.**

Обоснование (согласуется с research §2/§3):
- Нет чекаута → нет причины держать "state оплаты" где-то кроме браузера пользователя.
- Clerk в проекте есть, но используется только для `/dashboard` (кабинет клиента с уже смонтированными объектами) и `/admin` — вход не является предусловием для подбора оборудования (двойная аудитория брифа включает анонимных частников). Требовать логин ради корзины поднимет отток на входе, чего нет ни у одного паттерна из research §8.
- В кодовой базе нет ни одного стейт-менеджера (Zustand/Redux/Jotai нет в `package.json`) — весь существующий код на `useState`/`useEffect`/Context не используется вовсе. Вводить новую зависимость ради корзины из 5–20 позиций избыточно.

Реализация: `src/hooks/useCart.ts` — React Context + `useReducer`, синхронизация с `localStorage` через `useEffect` (тот же idiom, что `useLivePrices` в `Calculator.tsx` — fetch/effect с graceful fallback, только вместо fetch — `localStorage.getItem`/`setItem` с `try/catch` на случай приватного режима браузера или переполненного хранилища). Ключ `sba_equipment_cart_v1` — версионирование в ключе на случай будущей несовместимой миграции формата.

Что **не** делаем:
- Не пишем корзину в БД по каждому изменению (нет смысла без чекаута/кросс-девайс сценария, лишняя нагрузка на Neon).
- Не делаем "гостевые сессии" через cookie+БД — Clerk уже даёт auth, если понадобится персистентность между устройствами, это чистое включение опции "войти, чтобы сохранить корзину" поверх готового Clerk, не новая инфраструктура.

Персистентность **quote** (не корзины!) в БД происходит **только в момент явного действия пользователя** — "получить КП"/"скачать PDF"/"отправить заявку", ровно как сейчас `Calculator.tsx` шлёт в Telegram только по сабмиту формы, а не на каждое изменение слайдера. Это создаёт запись в `quotes` (§2.2) и одновременно уходит в Telegram тем же способом, что и сейчас (см. §5.4).

## 4. AI-режим (Gemini)

### 4.1 Эндпоинт

`api/ai-recommend.ts` — новый serverless-эндпоинт, POST, тело: `{ answers: QuizAnswers }`. Ключ `GEMINI_API_KEY` только на сервере (уже корректно заложено в брифе, не в клиентском коде) — паттерн идентичен `api/telegram.ts`/`api/users.ts`, где секреты читаются из `process.env` внутри `api/`.

### 4.2 Поток данных (важно — не "весь каталог + вопросы напрямую в LLM"):

```
1. Клиент отправляет ответы квиза (4-6 вопросов, см. research §8) → api/ai-recommend.ts
2. Сервер делает rule-based префильтр каталога в БД (Drizzle-запрос по products:
   environment, category, жёсткие теги из ответов — например "периметр" исключает
   category='access_control", "нужна ночная съёмка" фильтрует specs.nightVision=true).
   Это ТОТ ЖЕ фильтр, что используется и без AI (см. §5.2) — переиспользуемая функция,
   не код, дублированный между режимами.
3. Отфильтрованное подмножество (обычно 5-20 товаров, не весь каталог) сериализуется
   в компактный JSON и уходит в Gemini вместе с ответами квиза.
4. Gemini вызывается с responseSchema (structured output, НЕ function calling —
   обоснование см. research §5): схема ответа фиксирована —
   { bundles: [{ label, tier: "econom"|"optimal"|"premium", items: [{productId, qty}], reasoning }] }
   (2-3 bundle, ровно как зафиксировано в брифе).
5. Сервер валидирует ответ: каждый productId должен существовать в отфильтрованном
   наборе, отправленном в промпте (защита от галлюцинации несуществующего SKU —
   research 7.2). Невалидные productId в bundle — bundle отбрасывается целиком,
   не "чинится" молча.
6. Если после валидации осталось 0 валидных bundle — сервер отдаёт rule-based
   фоллбэк (см. 4.3), а не пустой ответ.
```

Ключевое архитектурное решение из research §5 применено буквально: **AI — надстройка над rule-based фильтром, не замена**. Это одновременно снижает стоимость/латентность вызова (меньше токенов в промпте) и риск несовместимых рекомендаций.

### 4.3 Лимиты и фоллбэк

- **Таймаут**: серверный вызов Gemini оборачивается в `Promise.race` с таймаутом (например 8с) — при превышении сразу отдаём rule-based результат, не держим пользователя на спиннере неопределённо долго.
- **Недоступность/ошибка Gemini API** (5xx, недоступен из РК/региональные ограничения — упомянуто в research как возможный риск): `try/catch` → тот же rule-based фильтр из шага 2, но без LLM-ранжирования/обоснования — просто возвращаем отфильтрованный набор как один bundle с дефолтной формулировкой. Это то же graceful degradation, что уже есть в `useLivePrices()` (fallback на `DEFAULT_PRICES` при недоступности `/api/prices`) —этот паттерн уже валидирован в этой кодовой базе, переиспользуем его идею, не код.
- **Rate limiting / контроль стоимости**: serverless-функции Vercel stateless между вызовами — in-memory счётчик не работает. Минимально достаточный вариант для MVP: простая таблица `ai_requests(ip_hash, day, count)` в той же Neon БД с upsert+инкрементом на каждый вызов и отказом (429) при превышении дневного лимита на IP (например 20/день) — не требует новой инфраструктуры (Redis/Upstash), использует уже подключённый Neon. Если объём вырастет, миграция на Vercel KV/Upstash — локализованное изменение одного эндпоинта.
- **Некорректный/не-JSON ответ модели**: `responseMimeType: "application/json"` + `responseSchema` резко снижает вероятность этого (Gemini structured output), но парсинг всё равно в `try/catch` — падение парсинга трактуется как "недоступность" из пункта выше, тот же фоллбэк.

### 4.4 Изоляция от вендора

Вызов Gemini инкапсулируется в `api/_lib/ai/geminiClient.ts` с интерфейсом `recommend(answers, catalogSubset): Promise<Bundle[]>`, не привязанным к деталям Gemini SDK в остальном коде `api/ai-recommend.ts`. Это прямая рекомендация research §5 ("миграция на OpenAI — замена одного serverless-эндпоинта") — реализуется тонкой прослойкой, не отдельным сервисом/очередью (излишне для объёма задачи).

## 5. Границы модулей / интерфейсы


### 5.1 Каталог (`src/lib/catalog.ts` + `api/products.ts`)
- Контракт: `GET /api/products?category=&environment=&q=` → `Product[]`. Фильтрация — `ILIKE`/точное совпадение по денормализованным колонкам (`category`, `environment`), без Elastic/Algolia (research §2 явно закрывает этот вопрос для 15–100 позиций).
- Экспортирует чистую функцию `filterCatalogByAnswers(products, answers): Product[]` — **единственное место**, где живёт rule-based логика подбора. Используется и страницей каталога (ручные фильтры на клиенте поверх уже загруженного списка), и `api/ai-recommend.ts` (серверный префильтр перед вызовом Gemini) — не два разных места с похожей, но дрейфующей логикой.

### 5.2 Корзина (`src/hooks/useCart.ts`)
- Контракт: `{ items: CartItem[], add(productId, qty), remove(productId), setQty(productId, qty), clear() }`. `CartItem = { productId, qty }` — денормализованные данные товара (имя/цена/фото) не хранятся в корзине, подтягиваются из каталога по `productId` при рендере/расчёте, чтобы избежать рассинхрона цены между "когда положили в корзину" и "когда считали смету" (актуально, т.к. `basePrice` может обновиться).

### 5.3 Смета (`src/lib/estimate.ts`)
- Контракт: `computeEstimate(cartItems: CartItem[], products: Product[], installParams: InstallParams): EstimateResult`.
- **Переиспользует** из `src/lib/pricing.ts` без изменений: `getHddCost()` (расчёт стоимости HDD по объёму архива), `HDD_RATES` (ГБ/день по разрешению — берётся из `specs.resolution` товара-камеры в корзине, с фоллбэком на "2MP" если камера кастомная без этого поля), `PRICES.install[objectType][installLevel]` (тарифы монтажа по типу объекта/сложности — те же, что в `Calculator.tsx`).
- **Не переиспользует** пошаговую arithmetic-логику `Calculator.tsx` напрямую (она инлайн в компоненте, не экспортируется) — вместо этого `estimate.ts` реализует параллельную, но идентичную по формуле логику для случая "монтаж по товарам из корзины, а не по абстрактным тирам": суммарная цена товаров корзины (реальная, не тирная) + кабель/гофра/HDD/монтаж (те же тарифные ставки из `pricing.ts`, что уже валидированы на старом калькуляторе). Итог: одна и та же ставка монтажа в двух местах, без риска для `Calculator.tsx`.
- Явно помечает в возвращаемом объекте, какая часть цены "точная" (сумма `basePrice` товаров) и какая "ориентировочная" (монтаж/кабель/HDD, зависящие от факта выезда) — см. §8, это прямое следствие research 4.2/7.3: разделение обязательно на уровне данных, а не только текста UI, иначе PDF/UI не смогут показать два разных дисклеймера консистентно.

### 5.4 PDF/КП (`src/lib/pdf/`)
Два шаблона (research 4.3, "два документа для двух аудиторий" — прямая точка входа для Tensions PM-агента, архитектурно закладываем возможность, финальное решение "делать ли оба на MVP" — за PM):
- `renderConsumerSmeta()` — эмоциональный формат, близкий к текущему PDF `Calculator.tsx` (фото товаров, крупный итог), для частника.
- `renderTenderQuote()` — табличный формат с местом под реквизиты компании (БИН, юр.адрес — поля берутся из `quotes.contactCompany` + статических реквизитов SBA), артикулами (`products.sku`), НДС отдельной строкой, сроком действия предложения — для снабженца.
Оба используют общий низкоуровневый адаптер `renderSmetaPdf()` (§1.2), различаются только DOM-шаблоном, который в них рендерится перед конвертацией.
Выбор шаблона — явный переключатель в UI корзины ("Скачать как КП для компании" / "Скачать смету"), не автоопределение по эвристике.

### 5.5 Точка сборки

`EquipmentPicker.tsx` — единственный компонент, который знает про все четыре модуля сразу и оркестрирует переходы между ними. Остальные модули друг про друга не знают напрямую (каталог не импортирует корзину, корзина не импортирует PDF) — тестируются независимо.

Правка нужна **только** если заводится отдельный `/katalog` роут и потребуется явно завести его в SPA-фоллбэк — но текущий финальный rewrite `"/(.*)" → "/index.html"` уже покрывает любой новый клиентский путь, так что и это, вероятнее всего, не требует правки `vercel.json`.

Устанавливаются стандартным `shadcn add`, не требуют инфраструктурных изменений, но это явный пункт объёма работ для PM/dev, не только "переиспользовать существующее".

Рекомендация: новые файлы (`api/*`, `src/lib/*`, `src/components/EquipmentPicker/*`) должны проходить существующий `npm run lint` (`eslint . --ext ts,tsx --max-warnings 0`) без исключений — не ослаблять правила ради новой фичи.

## 7. Стратегия масштабирования / наполнение каталога

Трафик — не драйвер архитектуры здесь (research уже закрыл вопрос: Postgres без спецсредств поиска достаточен для 15–100 товаров, Vercel serverless тривиально держит нагрузку небольшого регионального сайта). Драйвер — **лёгкость пополнения и редактирования каталога** (явно указано в брифе и подтверждено research как главная скрытая сложность, §7.1).

Три слоя, от простого к сложному, вводятся по мере роста потребности (не всё сразу на MVP):

1. **MVP: Drizzle Studio / прямой SQL.** Ручное наполнение 10–15 товаров силами Павла напрямую через `drizzle-kit studio` (уже в devDependencies) или прямой доступ к Neon-консоли — нулевые затраты на разработку UI, полностью закрывает CONCEPT-2026.md сценарий "ручной ввод для старта". Загрузка фото — через уже существующий `api/upload.ts`-паттерн (Vercel Blob), вручную подставляя вернувшийся URL в поле `images`.
2. **После MVP, если наполнение станет частым:** минимальная админ-CRUD-страница на уже существующем, но пустом роуте `/admin` (сейчас в `App.tsx` — пустой `SignedIn` блок без содержимого; т.е. эта правка не трогает роутинг/danger-zone логику, только добавляет контент внутрь уже защищённого блока) — форма создания/редактирования товара на shadcn-компонентах (`table`, `input`, `select` — см. §6). Не отдельное приложение, не отдельный деплой.
3. **Долгосрочно, если объём вырастет за пределы enum-категорий/десятков позиций:** миграция `productCategoryEnum` → таблица `categories`, добавление полнотекстового GIN-индекса по `specs`/`name` — оба шага локализованные ALTER/миграции, не требуют смены СУБД или инфраструктуры.

Отдельно — **процесс поддержания** (не только инструмент): архитектура не может решить организационную проблему "кто и как часто обновляет цены/фото" (research 7.1 прямо называет это главным риском протухания каталога), но может её облегчить техническим индикатором — поле `products.updatedAt` + простой отчёт/вью "товары, не обновлявшиеся > N дней" (SQL-запрос или строка в будущей мини-админке), чтобы деградация каталога была видна, а не тиха.

## 8. Технические риски

### 8.1 Риски, напрямую связанные с danger-zone компонентами (из research)

| Компонент | Риск для этой фичи | Митигация |
|---|---|---|
| `src/App.tsx` (4 бага) | Добавление `/katalog`-роута может задеть существующие Clerk-гарды (`/dashboard`, `/admin`) или порядок `<Route>`/catch-all `NotFound` | Делать аддитивным отдельным PR, вручную regression-тестировать `/dashboard`, `/admin`, `/uslugi/*` после мержа; при сомнении — отказаться от отдельного роута в пользу модалки (см. §1.1) |
| `src/i18n.ts` (3 бага, **один** язык `ru` внутри одного файла-объекта) | Все новые строки UI (квиз, каталог, корзина, КП) должны добавляться в тот же вложенный объект `resources.ru.translation` — большой объём новых ключей в одном файле повышает риск конфликтов при параллельной работе нескольких агентов/разработчиков над редизайном | Заводить новые ключи под отдельным неймспейсом (`picker.*`, `cart.*`, `catalog.*`), не переиспользовать/не редактировать существующие `calc.*` ключи — снижает вероятность merge-конфликтов и не трогает уже работающие переводы `Calculator.tsx` |
| `Hero.tsx`, `Footer.tsx`, `Statistics.tsx`, `Testimonials.tsx`, `Projects.tsx` (6–8 багов каждый) | Редизайн главной (вне периметра этого документа по содержанию, но CTA на новый пикер добавляются именно в `Hero`/`Footer`) — любое изменение в этих файлах статистически дороже, чем в среднем компоненте | Точечные, минимальные правки (добавить один `onClick`/проп для открытия `EquipmentPicker`, аналогично уже существующему `onOpenCalc`), не рефакторить компонент попутно; детальный план очерёдности редизайна — зона PM |
| `Calculator.tsx` (жёстко запрещено брифом) | Соблазн импортировать общий хук/тип напрямую из файла — любой импорт из danger-zone файла создаёт скрытую связь и риск, что будущая правка `Calculator.tsx` неожиданно сломает `EquipmentPicker` | Технический контракт: `EquipmentPicker`/новые модули **не импортируют ничего из `Calculator.tsx`**, только из `src/lib/pricing.ts` (уже общий, безопасный модуль) — см. §1.3 про дублирование `useLivePrices` |

### 8.2 Риски специфичные для новой фичи (из research §4/§7, спроецированные на архитектуру)

- **Точность AI-рекомендаций на реальных данных каталога** (research 7.2) — архитектурно риск снижен через (а) серверный rule-based префильтр перед LLM (§4.2), (б) валидацию `productId` из ответа против отправленного подмножества (§4.2 шаг 5), но **не устраняется полностью** — потребуется несколько раундов доработки промпта после наполнения каталога реальными товарами, что не решается на уровне архитектуры, только процессом тестирования (зона PM).
- **Юридическая согласованность "ориентировочных" цен по всем поверхностям** (research 4.2/7.3) — архитектурно закреплено в §5.3: `EstimateResult` явно разделяет "точную" (товары) и "ориентировочную" (монтаж) части на уровне данных, что даёт UI и обоим PDF-шаблонам единый источник истины для формулировок, вместо того чтобы каждая поверхность решала это заново текстом. Согласованность формулировок Hero/PainSection/корзины — не архитектурная, а контентная задача (PM/копирайтинг), но структура данных её не блокирует.
- **html2canvas на многостраничных tender-ready документах** (research §3/§5) — явный технический риск при росте числа позиций в корзине: `html2canvas` рендерит один `<canvas>` без разрывов страниц, длинная таблица позиций в `renderTenderQuote()` может обрезаться/масштабироваться некорректно на границе A4. Для MVP с ограниченным числом позиций в комплекте (обычно 5–15 строк) риск невысокий; если procurement-сценарии потребуют регулярно большие спецификации (30+ позиций), потребуется миграция `renderTenderQuote()` на серверный рендеринг (Puppeteer/Playwright в отдельной serverless-функции или React-PDF) — изолированная замена одного модуля (§5.4), не всей PDF-подсистемы.
- **Rate-limit / стоимость Gemini без выделенной KV-инфраструктуры** (§4.3) — использование Neon для счётчика запросов добавляет write-нагрузку на основную БД при всплеске трафика; для MVP-масштаба это некритично (research подтверждает низкий трафик), но если конверсия в AI-режим окажется высокой, стоит заранее заложить миграцию на Vercel KV/Upstash как быстрый next step, а не переделывать эндпоинт с нуля.
- **Рассинхрон цены товара между моментом добавления в корзину и расчётом сметы** — если `products.basePrice` изменится (ручное редактирование в Drizzle Studio) между визитами пользователя (при персистентной localStorage-корзине), сумма в корзине на старте показа может отличаться от последней сохранённой в `quote`. Митигация заложена в §5.2 (корзина хранит только `productId`+`qty`, цена всегда берётся из актуального каталога при рендере) — таким образом UI всегда показывает свежую цену, а не устаревшую, что для "ориентировочной" сметы приемлемо и даже желательно.
- **`quotes.aiTranscript` как потенциально чувствительные/объёмные данные** — хранение полного диалога квиз+ответ Gemini в jsonb на каждый quote может разрастись; для MVP не проблема, но стоит заложить (не обязательно реализовывать сразу) политику ретенции/очистки старых `aiTranscript`, если объём станет заметным — не блокер архитектуры, заметка на будущее.

## Резюме (для оператора цепочки)

Архитектура встраивает новую фичу как второй независимый модальный флоу на `Home.tsx` (по образцу уже работающего `Calculator`), не трогая его содержимое и не импортируя из него ничего — только `src/lib/pricing.ts` переиспользуется напрямую, а PDF-паттерн и `useLivePrices` копируются, а не импортируются, чтобы не создавать скрытую связь с danger-zone файлом. Новая модель данных — `products` (каталог SKU, jsonb-характеристики, денормализованный `environment` для быстрой фильтрации) и `quotes` (сохранённые расчёты для admin-видимости и tender-истории) — явно отделена от существующей `equipment_prices` (тирный ценовой кэш, не трогается). Корзина — localStorage + Context/useReducer без новых зависимостей и без БД (обоснование: нет чекаута, нет кросс-девайс требования); AI-режим — серверный эндпоинт с Gemini structured output, работающий **поверх** того же rule-based фильтра каталога, что и ручной подбор, с обязательной серверной валидацией `productId` и graceful fallback на чистый rule-based результат при недоступности/ошибке Gemini или превышении простого таблично-Neon rate-limit. Все инфраструктурные изменения укладываются в текущий Vercel/Neon/Drizzle-контур без новых сервисов; единственная потенциально рискованная точка касания — аддитивная правка `src/App.tsx` для нового `/katalog`-роута (опционально, можно избежать, оставшись на модалке). Главные технические риски вне контроля чистой архитектуры — это ровно те три ловушки из research (наполнение/поддержание каталога, доводка точности AI-рекомендаций, сквозная согласованность юридических формулировок) — архитектура закладывает для них структурные опоры (индикатор устаревания каталога, разделение точной/ориентировочной части сметы в данных, изоляция AI-вендора), но не устраняет их полностью — это ожидаемо, так как это не архитектурные, а продуктовые/процессные задачи. Файл сохранён в `/home/claude/sba/sba-security-landing/.wednesday/plans/architect.md`.
